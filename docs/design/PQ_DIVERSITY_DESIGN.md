# 設計メモ: 暗号の数学的多様化 — 符号ベース KEM の併用と3系統の AND 結合署名

nkct の耐量子性は、今のところ **すべて格子（Module-LWE / Module-SIS）に依っている**。
鍵交換は ML-KEM、認証は ML-DSA であり、併用している楕円曲線（P-256 / X25519 / Ed25519）は
量子計算機に対する保険にならない。本書は、格子とは別系統の数学に基づく方式を2つ足す設計を述べる。

- **A. 鍵交換**: ML-KEM と並べて **符号ベース KEM（HQC）** を使い、どちらか一方が残れば秘匿が保たれるようにする。
- **B. 認証**: ID を **Ed25519・ML-DSA・SLH-DSA（FIPS 205、ハッシュベース）の3つの鍵の組** にし、
  **要求された全員の署名が通ったときだけ** 受け入れる（AND 結合）。接続ごとのハンドシェイクは Ed25519 ‖ ML-DSA、
  鍵の配布やファイル署名のような一度きりの署名は3つすべてで署名する。

---

## 0. 背景と脅威モデル

### 0.1 きっかけ

2026 年に格子暗号の破綻を主張する論文が2本出た。どちらも現時点では否定されている。

| 主張 | 内容 | 状態（2026-11-27） |
|---|---|---|
| Luo, arXiv 2605.17412（2026-05） | CDPR の量子攻撃を拡張し ML-KEM-512/768/1024 を破る。論理量子ビット約 1,400 | 査読なし。攻撃対象が秘密鍵に依存しない等の致命的な誤りが指摘されている |
| Simon, ePrint 2026/1591（2026-08） | DCP の量子多項式時間解法 → 近似 SVP / LWE | Lemma 3 に反例。Gupte–Ragavan–Zhandry（ePrint 2026/1693）が不可能性を示した。著者は撤回していない |

**したがって本書は緊急対応ではない。** 「格子が破られたら全部が同時に倒れる」という構造上の単一障害点を、
標準化の進み具合に合わせて計画的に解消するためのものである。

### 0.2 脅威の場合分け

| 記号 | 想定 | 楕円曲線 | 格子 | 符号 / ハッシュ |
|---|---|---|---|---|
| T0 | 現状（CRQC なし、格子への有効な攻撃なし） | 安全 | 安全 | 安全 |
| T1 | CRQC が出現（Shor のみ） | **破綻** | 安全 | 安全 |
| T2 | 古典計算機で格子が破れる | 安全 | **破綻** | 安全 |
| T3 | 量子計算機で格子も破れる（今回の主張の型） | **破綻** | **破綻** | 安全 |

現行構成は T0 / T1 / T2 の一部に耐える。**T3 では鍵交換も認証もすべて破れる。**
T2 でも、鍵交換は ECDH が残るので秘匿は保たれるが、**認証は ML-DSA 単独なのでなりすましが成立する。**

### 0.3 鍵交換と認証で緊急度が違う

- **鍵交換（秘匿）は遡って破られる。** 今日の暗号文やセッションを録っておけば、将来破れた時点で読める
  （Harvest-Now-Decrypt-Later）。対策は「破られる前」に入れておかないと効かない。
- **認証は、その時点で破られなければよい。** 将来 ML-DSA が破れても、過去のハンドシェイクを遡って
  なりすますことはできない。破れた後の新しい接続だけが問題になる。

**理屈の上の優先度は A（鍵交換）> B（認証）。** ただし標準化の状況は逆で、SLH-DSA は FIPS 205 として
確定済みなのに対し、HQC（FIPS 207）は 2026-11 時点で公開ドラフトすら確認できない。
この食い違いの扱いは §7 で述べる（Phase 1 で B を先に入れ、Phase 2 で A を入れる）。

## 1. 現行の構成（main bb122aa9）

### 1.1 P2P ハンドシェイク（`src/p2p/processor.rs`）

- **鍵交換**: エフェメラル P-256 ECDH（`"prime256v1"` 固定、:1161 / :1590）と、エフェメラル ML-KEM
  （クライアントが接続ごとに ek を生成、サーバが encapsulate、:1163 / :1591）。
- **鍵導出**: `combined_ss = ss_ecdh ‖ ss_mlkem`（:1169-1171）。`salt = SHA3-256(transcript 全体)` とし、
  `HKDF-SHA3-256(combined_ss, salt, "nk-auth-v3")` で 88B を導出（:1250）。
  **ct と公開鍵は transcript を通じて salt に入る**ので、結合器として ct が束縛されている。
- **認証**: ML-DSA（`--dsa-algo`、既定 ML-DSA-65）のみ。sig_I は #1–#7、sig_R は #1–#12 に署名する。
  FIPS 204 の ctx は `"nkct-handshake-iroh-v1"`（:52）。
- **ピン留め**: 指紋は `SHA3-256(生の ML-DSA 公開鍵)`。ticket（`src/ticket.rs`）は `fp_algo` ビットマスク
  （bit0 = 署名、bit1 = 暗号化）と 32B 指紋2つを持つ。allowlist も同じ指紋が鍵になる。
- **バージョン交渉はない。** 両端が同じ `--kem-algo` / `--dsa-algo` を指定する前提で、版の区別は ALPN
  （`nkct/shell/2`、`nkct/scp/3` など、`src/network/mod.rs:36-69`）だけである。
- **サイズ上限**: `read_vec` が **ハンドシェイクの各フィールドを 8192B で打ち切る**（`src/network/mod.rs:748`）。
  ハンドシェイク後の AEAD パケットは 128 KiB（`src/shell.rs:41`）。

### 1.2 ファイル暗号化と署名（`src/strategy/`）

- ヘッダは `"NKCT"`、ver 3、strategy バイト（ECC=1 / PQC=2 / Hybrid=3）。Hybrid は ECC と PQC の
  サブヘッダを LP（長さ前置）で2つ並べる（`hybrid.rs:301-319`）。
- 鍵導出は `ss_ecdh ‖ ss_mlkem` を HKDF-SHA3-256 に通す（`hybrid.rs:187-191`）。
  **ct と公開鍵は KDF に入らない**。チャンクの AAD に入るセッション ID（`SHA-256(header)[..16]`）で
  束縛されているだけである。
- **"hybrid" モードの署名は ML-DSA 単独。** sign / verify はすべて PQC 側に委譲される
  （`hybrid.rs:86-90`）。ECDSA との合成は、AND でも OR でも行っていない。
- 上限: 復号時のヘッダ読み込み 16384B（`src/processor.rs:418`）、keyring の自動照合で覗く先頭 8192B
  （`main.rs:1450`）。

### 1.3 KeyBundle / keyring / pairing

- NKKB v1（`src/keybundle.rs`）: 所有者は ML-DSA 鍵で、鍵ごとの keybind 署名とバンドル全体の自己署名を持つ。
  usage は `0x01` = ML-KEM、`0x02` = P-256 hybrid。**アルゴリズム名はバンドルに入っておらず**、
  検証側が `"ML-DSA-65"` を固定で渡す（`main.rs:1313`、`pairing.rs:29`）。1フィールドの上限は 64 KiB。
- keyring（redb）の `my_identities` は `"handle:role:algo"` をキーにする。鍵種別は OID で判定するが、
  対応しているのは ML-KEM / ML-DSA / P-256 だけ（`keyring.rs:475-511`）。
- pairing はハンドシェイクの後、AEAD パケット1つで `LP(token) ‖ LP(bundle)` を送る（bundle 上限 256 KiB）。

### 1.4 MLS / PQFS / at-rest

- MLS は private suite `0xF101` を1つだけ使う。署名は **Ed25519 ‖ ML-DSA-65 の AND 結合**
  （`crypto_adapter.rs:602-691`）、KEM は X-Wing（X25519 + ML-KEM-768）。
- PQFS の prekey と NKB1 受信者バンドルは ML-DSA-65 固定で、署名の上限は 8 KiB（`prekey.rs:61`、
  `one_shot.rs:527`）。inbox の prekey blob も 8 KiB まで（`network/inbox.rs:228`）。
- at-rest は suite `0xF102`（X-Wing + HKDF-SHA512 + AES-256-GCM）。署名は使っていない。

### 1.5 横断的な問題

1. **ML-DSA-65 が、ID に署名する箇所すべてにハードコードされている**（KeyBundle、pairing、prekey、
   NKB1、MLS binding、MLS suite）。`--dsa-algo` が効くのはハンドシェイクとファイル署名だけである。
2. **rustcrypto バックエンドは KEM のパラメータセットを鍵長で選んでいる**（`rustcrypto_impl.rs:558-690`）。
   名前の引数は無視される。別系統の KEM を足すと、この推定は成り立たなくなる。
3. `--kem-algo` / `--dsa-algo` は値の検証がない自由文字列で、長さ表（`backend/mod.rs:141-184`）に
   載っていない名前は **長さ検査が素通りになる**（`None` を返して検査を飛ばす）。

## 2. 方式の選定

### 2.1 KEM: HQC を採り、Classic McEliece は採らない

| | HQC-128 | HQC-192 | HQC-256 | Classic McEliece 348864 | ML-KEM-768（参考） |
|---|---|---|---|---|---|
| 公開鍵 | 2,249 B | 4,522 B | 7,245 B | 261,120 B | 1,184 B |
| 暗号文 | 4,433 B | 8,978 B | 14,421 B | 96 B | 1,088 B |
| NIST カテゴリ | 1 | 3 | 5 | 1 | 3 |

HQC のサイズは Round 4 提出版の値で、FIPS 207 確定時に変わりうる。

**McEliece は採らない。** 理由は2つ。

- P2P ハンドシェイクは PQ-FS のため **接続ごとに KEM 鍵を生成する**。McEliece の鍵生成は重く、
  公開鍵（数百 KB〜1 MB）を毎回送るのは現実的でない。
- KeyBundle の 64 KiB、ハンドシェイクの 8 KiB など、ほぼすべての上限を桁違いで超える。

**HQC は、ML-KEM とは別の困難性（準巡回符号の復号）に基づき、NIST が 2025 年に ML-KEM の予備として選んだ方式である。**
サイズは ML-KEM の 2〜8 倍で、既存の設計にほぼそのまま収まる。

懸念点もある。

- 標準（FIPS 207）が未確定で、エンコードが変わりうる。
- 実装のタイミング攻撃が過去に複数報告されている。

### 2.2 署名: SLH-DSA と Ed25519

| | 公開鍵 | 署名 | 署名生成 | 検証 |
|---|---|---|---|---|
| Ed25519 | 32 B | 64 B | 非常に速い | 非常に速い |
| ML-DSA-65（現行） | 1,952 B | 3,309 B | 速い | 速い |
| SLH-DSA-128s | 32 B | 7,856 B | 非常に遅い（x86 で数百 ms 級） | 速い |
| SLH-DSA-128f | 32 B | 17,088 B | 遅い（x86 で数〜十数 ms 級） | 速い |
| SLH-DSA-192s | 48 B | 16,224 B | 非常に遅い | 速い |
| SLH-DSA-192f | 48 B | 35,664 B | 遅い | 速い |

署名生成の速度は一般的な目安で、未計測である。§7 の Phase 0 で計る。

- 安全性の根拠はハッシュ関数の性質だけで、T3 でも残る。
- ステートレスなので、LMS / XMSS と違って署名回数の状態管理が要らない。
- FIPS 205 は 2024 年に確定済み。
- **Ed25519 は量子計算機には耐えないが、T2（古典計算機での格子の破綻）と ML-DSA の実装バグへの保険になる。**
  鍵も署名も小さく速いので、接続ごとのハンドシェイクにも足せる。nkct では MLS ですでに Ed25519 ‖ ML-DSA-65 を使っている。

## 3. A: 鍵交換への HQC 併用

### 3.1 結合器

**3つの共有秘密を連結し、ct と公開鍵を束縛した上で KDF に通す。**

```
ikm  = ss_ecdh ‖ ss_mlkem ‖ ss_hqc
salt = SHA3-256(transcript)          … 全 ek / ct / 公開鍵を含む
okm  = HKDF-SHA3-256(ikm, salt, info = "<新ラベル>")
```

- P2P ハンドシェイクは、現行どおり transcript の salt で ct が束縛されるので、ikm の末尾に足すだけで済む。
  info ラベルは新しくする（例 `"nk-auth-v4"`）。旧版の鍵と同じ導出が別の入力から出ないようにするためである。
- **ファイル暗号化は現行の KDF が ct を束縛していない**（§1.2）。v4 ヘッダでは
  `salt = SHA3-256(ヘッダ全体)` に変え、KDF で直接束縛する。どちらか一方の KEM が CCA 安全でなくなった場合にも、
  結合が崩れないようにするためである（X-Wing と同じ考え方）。

### 3.2 P2P ハンドシェイク

- **フィールドの追加**: 初期化側が HQC のエフェメラル ek を送り（#4b）、応答側が HQC ct を返す（#9b）。
  どちらも transcript に LP で積む。transcript 内の順序はワイヤ上の順序と揃える。
- **版の切り替え**: ワイヤ上の交渉がないので、**新しい ALPN を割り当てる**（`nkct/shell/3`、
  `nkct/scp/4` など）。
  - 移行期間中、サーバは旧版と新版の両方の ALPN を受け付ける。
  - サーバ側のポリシーで新版だけを許可する設定も用意する。
  - flags バイト（#5）の予約ビットを使う案は採らない。旧サーバが未知ビットを拒否するので失敗は明確だが、
    ALPN で分けたほうが監査ログで区別しやすい。
- **上限**: 一律 8192B の `read_vec` を、フィールドごとに明示した上限を取る形に変える（例 `read_vec_max(stream, max)`）。
  HQC-192 の ct は 8,978B なので、一律の上限のままでは収まらない。
- **コスト**: 接続ごとの HQC 鍵生成・encapsulate・decapsulate と、送受信量の増分
  （HQC-192 で往復 +13.5 KB）。Pi 4 での実測が要る（§7 Phase 0）。

### 3.3 ファイル暗号化

- **新しい strategy バイト 4（"Multi"）** を足す。ヘッダは `LP(kem 名) ‖ LP(ct)` の並びを持つ汎用形式とし、
  将来の方式追加でヘッダ形式を変えずに済むようにする。既存の 1 / 2 / 3 は読み取り専用で残す。
- **受信者は HQC の静的鍵が必要になる。** 鍵管理への波及は次のとおり。
  - `gen-my-key` と keyring の種別判定に HQC を追加する。
  - KeyBundle に usage `0x03`（HQC enc）を追加する。
  - HQC には標準 OID が未割り当ての可能性がある。その場合は FIPS 207 の確定を待つか、
    private OID を使って後で置き換えるかを決める（§8）。
- **上限**: ヘッダ読み込みの 16384B と、keyring の自動照合で覗く 8192B を見直す。
  HQC-256 にハイブリッドのサブヘッダを足すと、16 KiB に近づく。

### 3.4 MLS / PQFS / at-rest

- MLS で KEM を替えるには **新しい private suite（例 `0xF103`）が必要**で、MLS はグループ内でスイートを変更できないので、
  **グループの作り直し** になる。mls-rs の `CombinedKem` は2方式の結合なので、3方式の結合は自作になる。
- prekey と NKO1 の上限（blob 8 KiB、enc 4 KiB）も HQC の ct では足りない。
- **影響範囲が最も広く、効果あたりの手間も最も大きい。** P2P とファイル暗号化の後に回す（§7 Phase 3）。

## 4. B: 3系統の AND 結合署名（Ed25519 ‖ ML-DSA ‖ SLH-DSA）

### 4.1 なぜ「証明書の連鎖」では足りないか

「SLH-DSA の長期鍵で ML-DSA 鍵に一度だけ署名しておき、ハンドシェイクでは ML-DSA だけを使う」構成は、
**T2 / T3 で守れない。** ML-DSA が破られると、攻撃者は **正規に認証された ML-DSA 公開鍵に対して署名を偽造できる**
（公開鍵から秘密鍵を復元するか、署名を直接偽造する）。連鎖の上位がいくら強くても、末端で破られる。

**したがって、追加する方式は、認証したい当のメッセージ（ハンドシェイクの transcript、KeyBundle の本体）に直接署名しなければならない。**

### 4.2 統一 ID と、頻度で分ける2つの署名プロファイル

**ID は最初から、3系統の鍵の組にする**: 楕円曲線（Ed25519）、格子（ML-DSA-65）、ハッシュ（SLH-DSA）。
署名するときは、対象の発生頻度に応じて使う鍵の組を切り替える。

- **指紋** は3つの公開鍵すべてを対象とし、ドメイン分離ラベルを入れる。

  ```
  fingerprint = SHA3-256("nkct-tri-id-v1" ‖ LP(ed25519_pub) ‖ LP(mldsa_pub) ‖ LP(slhdsa_pub))
  ```

  最初から3つの鍵を指紋に含めておけば、ピン留めのやり直しは移行時の1回で済む（§6）。
  ML-DSA 単独の指紋とはラベルで分離されるので、衝突しない。

- **署名対象**: Ed25519 には ML-DSA のような ctx 引数がないので、全員が同じ文字列に署名する。

  ```
  M' = "nkct-composite-sig-v1" ‖ LP(用途ラベル) ‖ SHA3-512(メッセージ)
  ```

  用途ラベルは、既存の ctx（`nkct-handshake-iroh-v1`、`nkct-bundle-v1`、`nkct-file-sign-v1` など）を流用する。
  ML-DSA と SLH-DSA には、FIPS 204 / 205 の ctx にも同じラベルを渡す。
  これで、ある用途の署名を別の用途へ流用することも、組から1つだけ抜き出して単独署名として使うこともできなくなる
  （IETF LAMPS の composite 署名と同じ考え方）。

- **署名の形式** は `LP(sig_ed25519) ‖ LP(sig_mldsa) [‖ LP(sig_slhdsa)]` とする。並べる順序は MLS（Ed25519 が先）に揃える。

- **検証** は、長さの完全一致を確認したうえで、要求される全員の署名が通ることを必須にする（AND 結合）。
  **どの組を要求するかは、署名者が送ってきた内容ではなく、検証側が用途から決める。**
  署名者が SLH-DSA の署名を省いて送ってきても、オフラインの用途なら拒否される。

- **2つのプロファイル**:

  | プロファイル | 署名 | 用途 |
  |---|---|---|
  | オンライン（2重 AND） | Ed25519 ‖ ML-DSA | 接続ごとのハンドシェイク |
  | オフライン（3重 AND） | Ed25519 ‖ ML-DSA ‖ SLH-DSA | 一度きりの署名（鍵の配布、ファイル署名） |

  重い SLH-DSA をハンドシェイクから外すことで、Pi 4 での接続時間の悪化と、`read_vec` の上限引き上げを避ける。

- **脅威ごとに守れる範囲**:

  | 想定 | オンライン（ハンドシェイク） | オフライン（KeyBundle、ファイル署名） |
  |---|---|---|
  | T1: CRQC が出現 | 守れる（ML-DSA が残る） | 守れる（ML-DSA と SLH-DSA が残る） |
  | T2: 古典計算機で格子が破れる | **守れる（Ed25519 が残る）** | 守れる（Ed25519 と SLH-DSA が残る） |
  | T3: CRQC で格子も破れる | **守れない** | **守れる（SLH-DSA が残る）** |
  | ML-DSA の実装バグ | 守れる（Ed25519 が残る） | 守れる |

  T2 でも守れるのは認証だけで、秘匿は §3（鍵交換）の範囲である。
  現行の「認証は ML-DSA 単独」という穴（§0.2）は、T2 については塞がる。

- **ticket**: `fp_algo` に bit2（3系統の統一 ID の指紋）を追加する。

### 4.3 適用箇所

| 箇所 | 署名の頻度 | プロファイル | SLH-DSA | 上限への影響 |
|---|---|---|---|---|
| KeyBundle（NKKB）の keybind と自己署名 | 鍵登録時だけ | 3重 AND | 128s（遅くてよい） | 64 KiB / フィールドで収まる。NKKB v2 として、3つの公開鍵とアルゴリズム ID を本体に入れる |
| pairing | 1回だけ | 3重 AND（KeyBundle に従う） | 128s | bundle 256 KiB で収まる |
| PQFS prekey、NKB1 | 鍵の補充時 | 3重 AND | 128s | 署名が約 11.2 KB になり、署名の上限 8 KiB と inbox の blob 8 KiB を引き上げる必要がある。一括補充の時間は Pi 4 で計測する（§7 Phase 0） |
| ファイル署名（NKCS） | ファイルごと | 3重 AND | 128s / f をユーザーが選ぶ | NKCS v3 で `LP(sig)` を並べる（現行の v2 は署名に長さ前置がない） |
| P2P ハンドシェイク sig_I / sig_R | **接続ごと** | **2重 AND** | **使わない** | 署名は 64B 増えるだけで、8192B の上限に収まる |
| MLS のメッセージ署名 | **メッセージごと** | 2重 AND（Ed25519 ‖ ML-DSA-65、現行のまま） | **採らない**（§9） | 変更なし |
| MLS の transport binding | epoch ごと | 検討対象（§8-4） | 128s / f | 16 MiB 以内 |

#### ハンドシェイクで送るもの

署名には SLH-DSA を使わないが、**SLH-DSA の公開鍵（32B）は送る。** 指紋は3つの鍵すべてから計算するので、
受け取った側が ticket や allowlist のピン留めと照合するには3つとも必要になる。

- #6 / #11（ML-DSA 公開鍵）を、3つの公開鍵の組 `LP(ed25519_pub) ‖ LP(mldsa_pub) ‖ LP(slhdsa_pub)` に置き換える。
  増分は約 70B で、transcript に入るので署名で束縛される。
- 形式が変わるので、§3.2 と同じく新しい ALPN を割り当てる。HQC の導入（Phase 2）でもう一度 ALPN が変わる。

#### ハンドシェイクで SLH-DSA を使わない理由

- 128f でも接続のたびに双方で署名を生成することになり、暗号拡張のない Pi 4 では接続時間（現状 0.125s）への影響が大きい。
- Ed25519 を足した2重 AND で、T2 と ML-DSA の実装バグには耐えられる。
- T3 のハンドシェイク認証はあきらめる。その代わり、SLH-DSA を使うかどうかのポリシー分岐も、ハンドシェイク中の交渉も要らなくなり、設計と実装が単純になる。
  T3 でも鍵の配布と署名済みファイルは守られるので、ハンドシェイクの外から信頼をやり直せる。

### 4.4 keyring

- `my_identities` に role `sign-ed25519` と `sign-slh` を足し、統一 ID は Ed25519 / ML-DSA / SLH-DSA の行の組として持つ
  （秘密鍵は既存と同じく暗号化 PKCS#8）。
- **ID 用の Ed25519 鍵は、iroh の通信路用の `node.key`（これも Ed25519）とは別に生成・管理する。**
  `node.key` は接続先アドレス（NodeId）であり、用途も保護の方針も違う。
- 種別判定に、Ed25519（RFC 8410）と SLH-DSA（NIST 割当済み）の OID を追加する。
- ed25519-dalek 3 は今は `mls` feature のときだけ有効なので、常に有効にする。openssl バックエンドは OpenSSL の Ed25519 を使う。

## 5. 前提となる改修（A / B 共通、先にやる）

1. **バックエンドの方式選択を名前ベースにする。** rustcrypto の `pqc_encap` / `pqc_decap` が鍵長で
   パラメータを推定している箇所をやめる。
2. **`--kem-algo` / `--dsa-algo` に値パーサを付ける。** 長さ表に載っていない名前で検査が素通りになる経路をなくす。
3. **上限をフィールドごとの明示値にする。** `read_vec` の一律 8192B、prekey / NKB1 / inbox の 8 KiB、
   NKO1 の 4 KiB、ヘッダ読み込みの 16 KiB を、方式ごとの最大長から導いた定数に置き換える。
4. **署名側のアルゴリズムを ID 形式に載せる。** NKKB などで `"ML-DSA-65"` を検証側が固定で渡している箇所をなくし、
   形式の中にアルゴリズム ID を持たせる。
5. **ドキュメントの訂正（独立して今すぐできる）**: "hybrid" モードのファイル署名は ML-DSA 単独であり、
   ECDSA との合成ではないことを SPEC / USAGE に明記する。

これらは単独でも価値がある（検査の素通り、暗黙の鍵長推定の解消）。

## 6. 移行と互換性

- **旧形式は読み取り専用で残す**: NKCT v3（strategy 1–3）、NKKB v1、NKCS v1/v2、旧 ALPN。
- **ピン留めのやり直し（1回だけ）**: 統一 ID の指紋は別の値になる。既存の ML-DSA 指紋から統一 ID へ移るには、
  **旧 ML-DSA 鍵で「新しい統一 ID への切り替え」に署名した声明** を配布する。受け取った側は、
  旧ピンで検証できればピンを付け替える（鍵ローテーションの既存手順 `docs/guides/KEY_ROTATION_GUIDE.md` に載せる）。
  SLH-DSA の鍵も最初から ID に入れておくので、このやり直しは1回で済む。
- **ダウングレード防止**: 統一 ID でピン留めした相手について、次のものは拒否する。
  - ハンドシェイクで、2重 AND（Ed25519 ‖ ML-DSA）に満たない署名（ML-DSA 単独など）
  - KeyBundle、pairing、prekey / NKB1、ファイル署名で、3重 AND に満たない署名

  要求する組は用途から検証側が決める（§4.2）。旧 ALPN を受け付けるかどうかは、サーバのポリシーで切れるようにする。
- **C++ 版（nkCryptoTool）には機能追加の予定がない**（今後は Rust 版一本で進める）。したがって新形式
  （NKKB v2 / NKCS v3 / strategy 4 / 新 ALPN）は Rust 版専用とし、C++ 版との相互運用は旧形式の範囲に限る。

## 7. 段階と優先順位

§0.3 のとおり、理屈の上では A（鍵交換）が先だが、**HQC の標準は未確定**で、今実装すると
FIPS 207 確定時にワイヤ形式を作り直すことになる。SLH-DSA は確定済みなので、先に進められる。

B は1つの Phase にまとめる。ハンドシェイクに SLH-DSA を入れないので、そのための `read_vec` の上限引き上げや
Pi 4 での接続時間の判断を待つ必要がなく、ID の移行も1回で済む。

| Phase | 内容 | 着手条件 |
|---|---|---|
| 0 | §5 の前提改修。Pi 4（暗号拡張なし）と x86 で SLH-DSA-128s/f・192s/f、HQC-128/192、prekey 一括補充の 3重署名時間を計測する | いつでも |
| 1 | B の一括実装: 3系統の統一 ID、P2P ハンドシェイクの2重 AND 化（新 ALPN）、オフラインの箇所（NKKB v2、pairing、prekey / NKB1、NKCS v3）の3重 AND 化、ID の移行手順 | Phase 0 の計測と、`slh-dsa` クレートの安定版（または openssl バックエンド限定で先行） |
| 2 | A の P2P ハンドシェイクとファイル暗号化（strategy 4、HQC 併用） | **FIPS 207 の確定**、または格子の暗号解析に信頼できる進展が出たとき（その場合は確定を待たず、ドラフト準拠で入れて後で追従する） |
| 3 | A の MLS / PQFS / at-rest（新 suite、グループの作り直し） | Phase 2 の運用実績 |

## 8. 未決定の論点

1. **HQC のレベル**: ML-KEM-768（カテゴリ 3）に揃えて HQC-192 にするか、保険と割り切って HQC-128 にするか。
   推奨は HQC-192。保険の側が弱いと、T3 で残る強度が下がるためである。
2. **SLH-DSA のレベルとハッシュ**: 128 と 192 のどちらにするか。SHA2 と SHAKE のどちらにするか
   （Pi 4 はどちらもソフトウェア計算になる）。特に、PQFS の prekey を一括補充するときの 128s の所要時間を
   Phase 0 で計測して決める。
3. **HQC の OID**: 標準 OID がない間、private OID で鍵ファイルを出すか、HQC 鍵を keyring 専用にするか。
4. **MLS transport binding に SLH-DSA を足すか**: epoch ごとなら負担は小さいが、MLS の外側で検証が要る。
5. **ライブラリ**:
   - rustcrypto 側の候補は `slh-dsa` 0.2.0-rc.5 と `hqc-kem` 0.1.0-rc.0 で、どちらも rc 版である。
   - OpenSSL は 3.5 以降が SLH-DSA に対応している。HQC への対応は未確認。
   - **付随的な発見**: `backend-openssl-vendored` は `openssl-src 400.0`（4.0.1）を直接依存に持つが、
     Cargo.lock 上の openssl-sys は `openssl-src 300.6.1+3.6.3` を使っている。
     実際にビルドされているのは **OpenSSL 3.6.3** と見られ、400.x の直接依存は機能していない可能性がある。別途確認する。
6. **楕円曲線を残すか**: 残す。T1 / T3 では役に立たないが、T2 と ML-DSA の実装バグに対する保険であり、実装の成熟度も高い。
   §4.2 の2重・3重 AND で Ed25519 を ID に入れるのも、同じ理由による。

## 9. やらないこと

- **Classic McEliece**: §2.1 の理由による。
- **MLS のメッセージ署名を SLH-DSA にする**: メッセージごとに 8–17 KB の署名と数 ms〜数百 ms の生成時間がかかり、
  チャットとして成り立たない。MLS の認証は Ed25519 ‖ ML-DSA-65 のままとし、多様化は binding（§8-4）で検討する。
- **LMS / XMSS（ステートフル）**: 状態の管理を誤ると致命的で、複数端末で ID を共有する使い方と相性が悪い。
