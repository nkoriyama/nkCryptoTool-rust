## 2. 主な脅威・脆弱性カテゴリ

1. **端末/GUI 表示偽装（サニタイズ漏れ）** — 最多の再発クラス。QUIC close reason・scp パス・
   ファイル名が `sanitize_for_terminal` を通らず運用者端末/監査ログ/GUI バナーへ
   （ターン1 F19/F20、ターン3 F1/F4/F5/F17/F18、ターン4 F1/F6、ターン5 F1/F2、
   ターン6 F4、ターン7 F2/F10/F11/F13）。サニタイザ自体の穴（Cf 書式文字、
   U+2028/29、U+200E/F）も別角度から複数回検出 → 根は同一で
   **S1 が7件を1つの根修正（単一述語への統一）で解消**。

2. **メモリ枯渇・P2P/リレー DoS** — inbox リレー中心に集中：POLL のバイト無制限展開
   （64MiB アップロードから最大16GiB の確保要求。A-F1/F9 と B-F5 は同一欠陥の
   保管層・handler 両面記述）→ S2、FETCH スロットル表の prune 不能（B-F1）+
   `accept()` 1回エラーでリレー全停止（B-F3）→ S3、DEPOSIT による他人キュー破壊
   （ターン3 F2、ターン4 F2）→ 容量到達拒否+7日TTL+送信者別バイト分割（`18a227a`）。

3. **ステートマシン競合・セッション寿命** — `CHAT_ACTIVE` の二重解放（B-F9）、
   GUI の孤児リスナー（B-F4）、プロセス全体共有のチャット入チャネル（B-F8）、
   GUI MLS イベントフィードが1フレームで死滅（ターン4 F3）、
   **グループ境界を跨ぐセッション殺害/配送停止（A-F6/F7）**、
   MLS per-group ロックの過剰保持（ターン2）、
   stale 行インデックスによるグループすり替え（ターン4 F5）。

4. **暗号メッセージの平文漏洩・PQ 特性剥奪** —
   **MLS Commit/Proposal が署名のみ平文（PublicMessage）**で第三者 inbox リレーに預けられ、
   メンバーシップ史+transport identity（ML-DSA 公開鍵=shell/forward 認可鍵）が再構成可能
   （A-F2/F5）＋SYNC 履歴で加入前 Commit の開示（A-F10）→
   AF2（`058835e8`、実測で flag day 不要と証明）+ S7（join-epoch クランプ）+ S12。
   プリキー枯渇による **耐量子前方秘匿性のダウングレード**（`MODE_STATIC_ONLY`）は
   ターン3 F11、ターン4 F4、ターン7 F6 と3回検出 →
   受信者別リザーブ+在庫高水位のストアアンカリング（`fdb80a23`）。

5. **認可/identity 境界** — 未認証の inbox ワイヤフィールド（recipient が任意32バイト）、
   scp mode の clamp 未適用（umask バイパス、ターン2 R2/R6、ターン3 F3/F14/F19）、
   GUI の `allow_unauth=true`、Welcome 自動参加による active group 再指向、
   NKCB バインディングの peer_id 自己主張、`NK_PASSPHRASE` の PTY 継承、
   チケット relay URL の無検証ダイヤル（SSRF、B-F7→S6）、OTP の argv 受入（ターン2）。

6. **at-rest ロールバック** — カウンタが KEK のみで DB に未束縛（A-F8）→
   実装は owner 判断で延期、検出可能範囲を文書化（`af4dd501`）。

## 4. 監査＋パッチ適用による堅牢性向上の総括

- **量的に**：82 検出、HIGH ゼロ。MEDIUM 中心で、「運用者端末の完全性」と
  「リレー可用性」の欠陥が主体だった。**「すべて閉じた」とは言えない**ので、内訳を
  正確に書く：ターン1・2・4 は全件修正。ターン3 は 19 件中 16 件をパッチ化し、
  **F2・F4 は2回ずつ拒否されてパッチ無し**（拒否理由は当該レポートに記録）。
  ターン5–7 は 25 件中 24 件をコードで修正し、A-F8 は文書のみ。ターン8 は 5 件すべてを
  コードで修正した。したがって残っているのは「明示的に受容し文書化した 3 件」であり、
  それらは `KNOWN_ISSUES.md` と各レポートから追える。
- **構造的に**（各修正がもたらした性質）：
  - 端末表示は**単一正規サニタイザ**の一元管理に（S1）— サニタイザ乖離という再発クラス
    自体を排除
  - inbox リレーは**バイト予算制**（POLL）+ **有界なスロットル表** + **耐障害 accept ループ**
    で、単発リクエストによる GiB 級増幅と恒久停止の両方を除去
  - **MLS 制御プレーンを PrivateMessage に封印**（AF2）— リレーがメンバーシップ史・
    transport identity を再構成できる経路を閉じ、実測により同時アップグレード
    （flag day）不要と証明
  - **グループ境界が信頼境界として機能する**ように：転送退避・recipient prune・
    セッション殺害・SYNC 履歴がいずれもグループ単位/参加 epoch 単位でスコープ化
  - **PQ 前方秘匿性が攻撃で持続的に剥奪されない**：リザーブの floor をストアに
    アンカーし、強制 prune によるリセットを不可に
  - GUI は**セッションスコープのチャネル・リスナーハンドル・ALPN ゲート**で、
    誤ったピア宛の平文送信や孤児リスナーを構造的に排除
- **残りの開示（KNOWN_ISSUES.md 項目9–12）**：
  1. FETCH 時のプリキー焼損（送信者側の緩和2案を拒否、`--strict-pqfs` で fail-closed 選択可）
  2. ストア全体の飽和。**inbox リレーの prekey 保存は 2026-08 サイクルで計測対象になったが、
     閉じてはいない** —— 固いバイト上限を作ったうえで撤回した。保持された上限は
     「リレー全体の恒久的で自己資金化する PQ-FS ダウングレードレバー」であり、
     上限なしの状態が持たない性質だったため（`ed8aa43b`、`KNOWN_ISSUES.md` 項目10）
  3. 制御メッセージの機密性は**送信側の性質**であり「最も更新の遅い commit 者と同じ程度に
     しか私的でない」
  4. グループメンバーは離脱を合成して recipient を落とせる（A-F7 経路2）。
     採用予定だった対処が現場で表現不能と判明したため記録に留めた

  いずれも「修正せず受容し文書化」した明示的な決定。
- **プロセス面で**：生成→検証→敵対的レビューのパイプライン、拒否理由の永続記録、
  `mandate_check.sh`（現在値は `bash scripts/mandate_check.sh` の最終行が出す）と
  `.security-baseline.sha256` によるゲート、
  スコープ分割による検証カバレッジの完全化（ターン5–7 で未投票23件→0）。
  ターン8 で `tests/`・CI ワークフロー・`scripts/` が走査され、**残る未スキャン領域は
  `docs/` と `android/` の 2 つ**になった（いずれも依頼で除外）。
  ただし**カバレッジ完全化は恒久的な性質ではない**：ターン8 では検証エージェント 12 体が
  評決を返さずに終了し、候補 4 件が 3 票そろわなかった。それらは所見として報告されず、
  「未検証」として当該レポートに列挙されている —— 再度パネルに掛ける価値がある。

  > **PASS の合計数はここに書かない。** 初版は「22」と書いており、それは執筆時点
  > （`b74afcd8`）で実測どおり正しかったが、翌コミットで古くなった。`50078278` が
  > Cargo.lock ベースライン検査を「diff の文字列を grep する」から「解決済み
  > バージョンを比較する」に直した結果、実在していたドリフトが WARN として報告
  > されるようになり 21 に下がり、F5 の修正で検査が 1 本増えて 22 に戻った。
  >
  > つまりこの数は**検査の本数と正直さの両方で動く**。合計点を品質の指標として
  > 読むと、「検査が正直になったので下がった」を後退と取り違え、**最も安く点を
  > 上げる方法が「検査を落ちにくくすること」になる**。だから文書には数を固定せず、
  > 取り方だけを書く。
- **恒久的に残った機構**（検出件数と違い、これが次のサイクルにも効き続ける部分）。
  ターン5–7 から 2 つ、ターン8 から 5 つ：
  - **`scripts/check_roster_sync_sections.sh`**（`24b7a217`）。ロスターの
    read-modify-write は suspension point を挟めない。それは**コメントが保持する規約で、
    CI から完全に不可視**だった —— 破れてもテストは全部緑のまま、
    `clippy::await_holding_lock` は `std::sync` のガードを対象とし tokio のガードを
    意図的に見逃す。該当区間を非 `async` 関数に切り出したので `.await` はコンパイル
    エラーになり、スクリプトは「関数を `async` に戻す」という残る唯一の穴を
    **fail closed** で塞ぐ（アンカーの改名やファイル欠落もエラー）。
  - **CI が `mls` を lint するようになった**（`5a18565b`）。それまで CI の
    clippy はどの起動も `mls` を含んでおらず、`src/group/` 全体がコンパイルもテストも
    されるのに lint だけ一度も掛かっていなかった。穴は広がりつつあり、
    直前の 3 本のセキュリティパッチはすべて `src/group/` を触っていた。
  - **`scripts/check_workflow_triggers.py` ＋ `scripts/test_check_workflow_triggers.sh`**
    （`f6c94af8`、ターン8 F5）。ワークフローを grep せず**パースする**。正規表現では
    「トリガの宣言」と「その語への言及」を区別できず、これは構造の違いなので、
    検査を広げても直らない。パースに移したことで誤検出3件と見落とし5形態が同時に消えた。
    **罠は PyYAML が YAML 1.1 パーサであること**：`on:` は文字列 `'on'` ではなく真偽値
    `True` に強制されるので、素直に `doc.get('on')` と書いた実装は**全ワークフローを
    clean と報告する**（silent fail-open）。`True` キーを受ける分岐を消すとテストが 6 件落ちる。
    そして検査器自身のテストをゲート項目 **18b** として登録してある —— テストファイルが
    消えるだけでリリースが赤くなる（検査器は fail-open へ 1 編集の距離にあり、
    その状態でも 8a は OK と表示するため）。
  - **`scripts/ci_apt.sh` ＋ `scripts/test_ci_apt.sh`**（`7ac84bcc`）。apt には**接続ごとの
    既定タイムアウトが無い**ので、接続を受理してから送信を止めるミラーは無限に待たせられる。
    実際に 2 ワークフローが 39 分停止し、**GitHub 上は「cancelled」と表示された** ——
    人間が止めたように読める。`Acquire::*::Timeout` と外側の `timeout` で
    「ハング」を「再試行可能な失敗」に変える（再試行だけでは効かない。何も失敗しないので）。
    偽 apt を注入する自己テストを CI の `repo-integrity` ジョブが毎回走らせ、
    ハング系ケースは外側 `timeout` で括ってある —— **落ちるべき所でハングするテストは
    悪いテスト**で、停止をゲートからテストへ移すだけになるため。
  - **`cargo audit` が release-blocking**（`c9c83de9`、命名の訂正が `31fe35e4`）。
    それまで job 単位の `continue-on-error: true` が付いており、勧告が出ても CI は緑だった。
    例外は `.cargo/audit.toml` に書く監査可能な形だけに残した。
  - **inbox リレーのログ 2 行の分離ゲート**（`b955c49e`）。`LogGate` を 1 行につき
    1 インスタンス持たせ、**リレー自身の失敗（`Storage` / `AtRest`）はゲートの外**に出す。
    共有ゲートを 1 つ置く版を実測したところ、60 秒窓を 1 バイト（`0x7f`）で占有するだけで
    後続の `No space left on device` 501 件が**1 行も出なくなった** ——
    未認証ピアが 1 分あたり 1 バイトで運用者の自己申告を消せる能力を買えてしまう。
    `KNOWN_ISSUES.md` 項目 10 の残余はこれでクローズした。**その項目の助言のうち
    「`Io` もゲートの外へ」は誤り**で、`Io` は本番経路のどこでも明示構築されず
    （構築は分類を固定するテスト 1 箇所だけ）、サーバ経路では 31 の
    `read_timed`/`write_timed`（ピアのストリーム）からしか来ない。
    外に出せば別の variant で同じ穴が開く。
  - **リリースゲートの検査本数の床**（`mandate_check.sh` 項目22）。上の各検査は
    「走って異議を唱えたとき」しか FAIL を出さない。**走らなくなった検査は何も出さず**、
    summary はそれに気づかなかった —— 検査ブロックを 1 本まるごと消すと PASS が 22→21 に
    なるだけで「all required checks passed」・exit 0（F2 の実測どおり。床を入れた後の
    同じ削除は exit 1）。床は **PASS ではなく合計（PASS+FAIL+WARN）**に置いた。これは
    好みではなく実測による：同一ツリーがローカルで PASS=22 WARN=2、CI で PASS=21 WARN=3 を
    出す（項目19 がリポジトリ外の `../issue/nkCryptoTool-rust` を見るため）。
    **内訳は環境で動くが、走った検査の本数は動かない。** 下回れば FAIL、上回れば WARN
    （検査を足したコミット自身をブロックしないため）。
    なお**弱体化は捕まえない** —— FAIL を WARN に変えた検査は走り続けて数にも入るので
    床は黙る（実測: 項目19 を WARN に戻して baseline を消すと 24本・exit 0）。
    そちらは F2 の warn→fail 昇格が担っており、両者は補完関係で、どちらも他方を含まない。

**一句で言えば**：ターン1–3で「表示偽装・認可・割当」の土台を固め、ターン4以降で
「リレー可用性」と「MLS 制御プレーンの平文性」というより深い設計問題に到達し、
第5–7ターンの分割走査で `src/` のカバレッジを完全化し、第8ターンで
**監査機構そのもの**（リリースゲート・CI・テスト）に走査対象を向けた。修正フェーズでは「修正そのものへの再監査」
（S7/S12 の多回拒否、A-F6 誤計上の訂正）を含む閉ループが回った。
82 件のうち残るのは**明示的に受容し文書化した 3 件**である（いずれもターン3・5–7 由来。
ターン8 は残ゼロ）。

## 5. この分析自体が示している弱点

閉ループが回ったことは事実だが、**同じ欠陥クラスが最後まで「捕まえる」だけで
「無くす」ことができなかった**ことも同じくらい記録に値する。

**コードが実装していない保護を主張するテキスト。** これはほぼ全パッチに現れ、
S12 では撤回済みの主張が5回の掃引を生き延びて6箇所に存在し、うち1箇所は
**同じファイルが doc コメントで主張して490行下の assertion で禁じている**状態だった。
最終的に効いた対策は安く、そして手動である —— **出荷前に diff を
`never` / `cannot` / `only` / `all` で grep し、それぞれについて真にしているコードを
名指しするか、スコープを狭める。**

**帳簿の失敗が2件。** A-F6 は engagement のほぼ全期間クローズと数えられていた
（同じ関数の別経路に6ラウンド費やしたことで、タリー上そこに畳み込まれた）。
そして生のテスト件数を feature 文字列の違うラン間で比較し、再現できない数値が
生まれた —— **有効な検査はカウントではなく、base に対する
テスト名集合の比較**である（「黙って飛ばされたテストがあるか」に答えられるのはこちらだけ）。

**構造的にテスト不能な箇所が残った。** A-F6 修正の2つの呼び出し側は、
`listen_loop` が実プロセスの stdin を読むためテストから駆動できず、
両者の一致はレビュー由来の保証にとどまる。テストの doc がそう明記している。
